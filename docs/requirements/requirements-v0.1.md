# LabKeeper 核心需求说明 v0.1

> 状态：需求基线，尚未实现。本文描述的是后续开发和测试目标，不代表功能已经完成。

## 1. 项目目标

LabKeeper 面向学校实验室或小型工作室，用于替代分散的 Excel 和纸质登记，形成设备预约、审批、签到、归还、耗材台账、提醒和审计的完整业务闭环。

第一版采用单体架构，在一台普通开发电脑上运行，不引入微服务、分布式事务或 Kubernetes。

## 2. 用户角色与数据范围

权限判断分为两层：

1. 角色权限：用户能否执行某类操作；
2. 数据范围：用户能否操作当前实验室或当前业务记录。

| 角色 | 核心职责 | 数据范围 |
| --- | --- | --- |
| 普通成员 | 查询设备、提交和取消本人预约、查看本人记录、申请耗材领用和退回 | 本人业务数据，以及设备公开信息和占用时段 |
| 实验室管理员 | 维护设备、审批预约、确认签到和归还、处理违约 | 被授权实验室的设备和预约 |
| 耗材管理员 | 维护耗材、执行入库和发放、确认退回、查看库存与流水 | 被授权实验室的耗材和库存流水 |
| 系统管理员 | 管理用户、角色、实验室授权、系统配置和操作日志 | 全系统账号、权限、配置及审计数据 |

### 2.1 角色边界

- 普通成员不能审批预约、修改他人预约或直接修改库存；
- 实验室管理员不能审批自己提交的预约；
- 耗材管理员不能直接覆盖当前库存数字或修改历史流水；
- 系统管理员默认不代替业务管理员执行审批和出入库；
- 一个用户可以拥有多个角色，但仍需遵守数据范围和禁止自我审批等业务规则；
- 普通成员只能看到某时段已占用，不能看到占用者的个人信息。

## 3. 设备预约生命周期

```text
提交预约
   │
   ▼
待审批 PENDING
   ├── 审批通过 ──► 已通过 APPROVED
   │                  ├── 取消 ──► 已取消 CANCELLED
   │                  ├── 签到 ──► 使用中 CHECKED_IN
   │                  │              ├── 按时归还 ──► 已完成 COMPLETED
   │                  │              └── 超时未还 ──► 已逾期 OVERDUE
   │                  │                                  └── 归还 ──► 已完成 COMPLETED
   │                  └── 超过签到期限 ──► 未签到违约 NO_SHOW
   ├── 审批驳回 ──► 已驳回 REJECTED
   └── 用户取消 ──► 已取消 CANCELLED
```

| 当前状态 | 操作 | 操作者 | 下一状态 |
| --- | --- | --- | --- |
| `PENDING` | 审批通过 | 实验室管理员 | `APPROVED` |
| `PENDING` | 审批驳回 | 实验室管理员 | `REJECTED` |
| `PENDING` | 取消 | 预约人 | `CANCELLED` |
| `APPROVED` | 取消 | 预约人或实验室管理员 | `CANCELLED` |
| `APPROVED` | 确认签到 | 实验室管理员 | `CHECKED_IN` |
| `APPROVED` | 超过签到期限 | 定时任务 | `NO_SHOW` |
| `CHECKED_IN` | 确认归还 | 实验室管理员 | `COMPLETED` |
| `CHECKED_IN` | 超过结束时间 | 定时任务 | `OVERDUE` |
| `OVERDUE` | 确认逾期归还 | 实验室管理员 | `COMPLETED` |

未列出的状态转换一律禁止。取消、驳回和违约必须保留原记录及原因，不能通过删除记录实现。

### 3.1 预约时间规则

- 时间按 30 分钟粒度选择；
- 单次预约时长为 30 分钟至 4 小时；
- 最早可提前 7 天预约；
- 最晚需提前 30 分钟提交；
- 默认签到窗口为开始前 15 分钟至开始后 15 分钟；
- `PENDING`、`APPROVED`、`CHECKED_IN` 和 `OVERDUE` 视为占用时段；
- 同一设备的有效预约时段不能重叠；
- 已批准预约需要改时间时，应取消后重新提交；
- 已产生历史业务的设备不能物理删除，只能停用或逻辑删除。

时间限制后续应配置化，不能散落硬编码在业务方法中。

## 4. 耗材库存流程

库存由“当前库存”和“不可随意修改的库存流水”共同构成。任何库存变化都必须关联业务单据。

### 4.1 入库

```text
创建入库草稿 DRAFT
   ├── 取消 ──► CANCELLED
   └── 确认 ──► 增加库存 + 写入 INBOUND 流水 + COMPLETED
```

库存更新、流水写入和入库单完成必须处于同一事务中。

### 4.2 领用

```text
成员提交申请 PENDING
   ├── 成员取消 ──► CANCELLED
   ├── 管理员驳回 ──► REJECTED
   └── 管理员确认发放
          └── 原子扣减库存 + 写入 ISSUE 流水 + ISSUED
```

`PENDING` 不预占库存。管理员实际发放时才执行带库存条件的原子扣减；库存不足时整次发放失败，不自动部分发放。

### 4.3 退回

```text
成员关联原领用记录并申请退回 RETURN_PENDING
   ├── 管理员拒收 ──► RETURN_REJECTED
   └── 管理员确认 ──► 增加库存 + 写入 RETURN 流水 + RETURN_COMPLETED
```

累计退回数量不能超过原领用数量。只有未使用且符合再次发放条件的耗材才能正常退回。

### 4.4 流水要求

每条库存流水至少记录：

- 耗材和所属实验室；
- 流水类型；
- 变化数量；
- 变化前库存和变化后库存；
- 关联业务单号；
- 操作人、操作时间和备注。

流水确认后不能修改或物理删除。

## 6. 统一业务规则

### 6.1 权限

- 停用用户不能登录；
- 接口同时校验角色权限和数据范围；
- 实验室管理员不能审批自己的预约；
- 密码、令牌等敏感信息不能写入日志。

### 6.2 预约

- 只有可用设备能接受新预约；
- 开始时间必须早于结束时间；
- 同一设备有效预约时段不能重叠；
- 状态只能按预约状态机转换；
- 取消、驳回和违约必须记录原因。

### 6.3 库存

- 入库、领用和退回数量必须大于零；
- 领用使用带库存条件的原子扣减，不能依靠“先查再扣”；
- 库存、业务状态和流水在同一事务内更新；
- 同一业务申请只能成功确认一次；
- 退回必须关联原领用记录；
- 当前库存小于等于库存下限时触发提醒。

### 6.4 消息与审计

- 只有数据库事务提交成功后才产生业务提醒；
- 消息消费者必须处理重复消费；
- 消息失败需要重试，最终失败进入死信队列；
- 预约、审批、签到、归还、库存变化和权限变更必须记录操作日志。

## 7. 关键验收场景

### 7.1 预约冲突

假如设备 A 已有 09:00 至 10:00 的有效预约，当另一用户申请 09:30 至 10:30 时，新预约必须失败，数据库中不能出现两条合法的重叠预约。

### 7.2 并发领用

假如某耗材库存为 10，两个请求同时各领用 8，最终只能一个成功、另一个库存不足，最终库存应为 2，并且只能生成一条成功领用流水。

该场景是后续并发测试目标，不是当前已经取得的测试结果。

### 7.3 逾期归还

预约签到后超过结束时间仍未归还时，定时任务将其标记为 `OVERDUE` 并生成违约记录；之后确认归还可进入 `COMPLETED`，但违约历史必须保留。

### 7.4 重复确认领用

领用申请已经发放成功后，再次确认必须被拒绝，库存和流水均不能重复变化。

## 8. 第一版范围边界

第一版包含：

- 单体后端和单个 Vue 前端；
- 多实验室及 RBAC 数据范围；
- 设备预约、耗材台账、提醒和审计；
- 单机 Docker Compose 开发环境。

第一版不包含：

- 微服务、分布式事务和 Kubernetes；
- 财务结算；
- 硬件门禁和真实扫码设备；
- 多级复杂审批；
- 跨组织多租户；
- AI 预测和智能推荐。
