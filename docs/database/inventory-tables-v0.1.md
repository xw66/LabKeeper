# LabKeeper 耗材库存表与并发约束设计 v0.1

> 范围：耗材、当前库存、入库、领用、退回和库存流水。本文不包含最终建表 SQL。

## 1. 本任务解决的问题

库存模块必须同时保存“现在还有多少”和“为什么变成这个数量”。它还需要保证：

1. 两个并发领用请求不能把库存扣成负数；
2. 同一业务单不能被重复确认；
3. 退回总量不能超过原领用量；
4. 业务状态、库存和流水要么一起成功，要么一起回滚；
5. 低库存提醒只能基于已经成功提交的库存变化。

本设计使用 6 张候选表：

- 耗材 `consumable`；
- 当前库存 `consumable_stock`；
- 入库单 `stock_inbound`；
- 领用申请 `issue_request`；
- 退回申请 `return_request`；
- 库存流水 `stock_ledger`。

## 2. 为什么资料、当前库存和流水要分开

```text
consumable
    保存名称、规格、单位等相对稳定的资料

consumable_stock
    保存当前数量和库存下限，是并发更新热点

stock_ledger
    保存每次增减的历史，不允许随意修改
```

如果全部放在耗材表中，会产生两个问题：

- 查询或修改名称等资料时容易误碰库存字段；
- 只能看到当前数字，无法解释库存变化过程。

当前库存是业务结果，库存流水是审计证据，两者不能互相替代。

## 3. 耗材表 `consumable`

### 3.1 业务职责

保存实验室内一种耗材的基础资料。第一版中，同一种物品在不同实验室分别建立耗材记录，库存互不混用。

### 3.2 字段候选

| 字段 | 逻辑类型 | 必填 | 唯一性意图 | 说明 |
| --- | --- | ---: | --- | --- |
| `id` | 标识 | 是 | 主键 | 耗材内部标识 |
| `laboratory_id` | 标识 | 是 | 参与组合唯一 | 所属实验室 |
| `consumable_code` | 短文本 | 是 | 实验室内唯一 | 稳定业务编码 |
| `consumable_name` | 短文本 | 是 | 否 | 显示名称 |
| `specification` | 短文本 | 否 | 否 | 规格，例如 500mL/瓶 |
| `unit` | 短文本 | 是 | 否 | 库存计量单位，例如瓶、盒、千克 |
| `status` | 状态 | 是 | 否 | `ACTIVE` 或 `DISABLED` |
| `description` | 长文本 | 否 | 否 | 使用说明或存储要求 |
| `created_at` | 时间 | 是 | 否 | 创建时间 |
| `updated_at` | 时间 | 是 | 否 | 最后更新时间 |
| `created_by` | 标识 | 否 | 否 | 创建人 |
| `updated_by` | 标识 | 否 | 否 | 最后修改人 |

耗材名称不单独全局唯一，因为不同规格或不同实验室可能使用相同名称。稳定编码才是业务识别依据。

## 4. 当前库存表 `consumable_stock`

### 4.1 业务职责

保存一种耗材的当前可用数量和低库存阈值，是领用、入库和退回共同更新的并发热点。

### 4.2 字段候选

| 字段 | 逻辑类型 | 必填 | 唯一性意图 | 说明 |
| --- | --- | ---: | --- | --- |
| `id` | 标识 | 是 | 主键 | 库存记录标识 |
| `consumable_id` | 标识 | 是 | 全局唯一 | 保证一种耗材只有一条当前库存 |
| `available_quantity` | 数量 | 是 | 否 | 当前可领用数量，不能小于零 |
| `minimum_quantity` | 数量 | 是 | 否 | 低库存提醒阈值，不能小于零 |
| `version` | 版本 | 是 | 否 | 候选乐观锁版本 |
| `created_at` | 时间 | 是 | 否 | 库存记录创建时间 |
| `updated_at` | 时间 | 是 | 否 | 最近一次库存变化时间 |

数量必须使用精确数值语义，不能使用二进制浮点数。具体精度和小数位在字段类型任务中决定，以同时支持“5盒”和“1.25千克”等计量方式。

`available_quantity` 不能通过普通编辑接口覆盖，只能由确认入库、确认发放和确认退回三个业务入口改变。

| `issue_request_id` | 标识 | 是 | 否 | 原领用申请 |
| `laboratory_id` | 标识 | 是 | 否 | 实验室数据范围 |

| `status` | 状态 | 是 | 否 | `PENDING`、`REJECTED` 或 `COMPLETED` |
| `completed_by` | 标识 | 否 | 否 | 确认接收的管理员 |

## 8. 库存流水 `stock_ledger`

### 8.1 业务职责

记录每次已确认库存变化，是库存台账和问题排查依据。流水只追加，不提供普通修改和删除能力。

### 8.2 字段候选

| 字段 | 逻辑类型 | 必填 | 唯一性意图 | 说明 |
| --- | --- | ---: | --- | --- |
| `id` | 标识 | 是 | 主键 | 流水内部标识 |
| `ledger_no` | 短文本 | 是 | 全局唯一 | 流水业务编号 |
| `laboratory_id` | 标识 | 是 | 否 | 实验室数据范围 |
| `consumable_id` | 标识 | 是 | 否 | 变化耗材 |
| `business_type` | 状态 | 是 | 参与组合唯一 | `INBOUND`、`ISSUE` 或 `RETURN` |
| `business_id` | 标识 | 是 | 参与组合唯一 | 对应业务单内部标识 |
| `quantity_change` | 数量 | 是 | 否 | 带符号变化量，领用为负数 |
| `quantity_before` | 数量 | 是 | 否 | 变化前库存 |
| `quantity_after` | 数量 | 是 | 否 | 变化后库存 |
| `operator_id` | 标识 | 是 | 否 | 确认业务的管理员 |
| `occurred_at` | 时间 | 是 | 否 | 库存变化发生时间 |
| `remark` | 长文本 | 否 | 否 | 备注 |
| `created_at` | 时间 | 是 | 否 | 流水创建时间 |

`business_type + business_id` 必须唯一，阻止同一业务重复生成流水。

这种多态引用让一张流水表能够关联三种业务单，但普通外键无法直接验证 `business_id` 是否属于对应业务表。第一版由业务事务、唯一约束和测试共同保证，后续在最终表设计时再次评估多个可空外键方案。

## 9. 确认入库的事务边界

```text
1. 按“入库单ID + DRAFT状态”更新为 COMPLETED
2. 如果影响行数不是1，拒绝重复或非法确认
3. 原子增加当前库存
4. 读取变化后的库存并计算变化前库存
5. 插入唯一的 INBOUND 库存流水
6. 提交事务
```

任何步骤失败都抛出异常并回滚。不能出现入库单已完成但库存没有增加，或库存增加却没有流水的情况。

## 10. 确认领用的原子扣减

错误流程：

```text
查询库存为10
判断足够
无条件扣减8
```

两个请求可能同时读到10并都判断足够。

正确流程使用数据库带条件的原子更新语义：

```text
只有 available_quantity >= 领用数量时才执行扣减
```

完整事务顺序：

```text
1. 按“领用申请ID + PENDING状态”更新为 ISSUED
2. 如果影响行数不是1，拒绝重复确认
3. 尝试带库存条件的原子扣减
4. 如果库存更新影响行数为0，抛出库存不足异常
5. 在同一事务中读取扣减后库存
6. 计算扣减前库存 = 扣减后库存 + 领用数量
7. 插入唯一的 ISSUE 库存流水
8. 提交事务
```

第1步在事务尚未提交时，其他事务看不到一个真正完成的 `ISSUED` 结果。如果后续库存不足，整个事务回滚，申请仍然保持 `PENDING`。

### 10.1 两个并发请求各领用8

初始库存为10：

```text
请求A：尝试扣减8
请求B：尝试扣减8
```

数据库会串行化对同一库存行的更新：

- 第一个成功后，库存变为2；
- 第二个继续判断时，`2 >= 8` 不成立；
- 第二个库存更新影响行数为0，整个事务回滚；
- 最终库存为2，只产生一条成功领用流水。

这个结果必须在后续使用真实并发测试验证，当前只是设计目标。

## 11. 确认退回的并发控制

仅查询“还可以退多少”再增加库存同样不安全。两个并发退回都可能读取相同的剩余可退数量。

确认退回事务：

```text
1. 按“退回申请ID + PENDING状态”更新为 COMPLETED
2. 如果影响行数不是1，拒绝重复确认
3. 条件累加原领用单的 returned_quantity
   条件：returned_quantity + 本次退回量 <= 原领用量
4. 如果影响行数为0，抛出超量退回异常
5. 原子增加当前库存
6. 读取变化后库存并计算变化前库存
7. 插入唯一的 RETURN 库存流水
8. 提交事务
```

因此两个并发退回不能共同突破原领用数量上限。退回申请状态、累计退回量、当前库存和流水会一起提交或一起回滚。

## 12. 为什么事务中更新后再读取库存是安全的

带条件的库存更新会锁定对应库存行直到事务结束。同一事务随后读取该行时，能够看到自己的更新结果；其他修改同一行的事务需要等待。

因此可以：

```text
先执行原子更新
再读取 quantity_after
根据变化量计算 quantity_before
```

这与“事务外先查询、之后无条件更新”不是同一种做法。后者没有把判断和扣减绑定为一个原子条件。

## 13. 低库存提醒的时机

在库存事务中可以判断：

```text
quantity_after <= minimum_quantity
```

但不能在事务提交前直接向 RabbitMQ 发送最终业务提醒，否则数据库回滚后可能留下虚假消息。

当前只确定原则：

```text
库存事务成功提交
    ↓
记录或发布低库存事件
    ↓
RabbitMQ 异步处理提醒
```

消息事件如何保证最终发布，将在消息阶段结合 `MessageEvent` 设计。

## 14. 索引与唯一性意图

| 表 | 约束或索引意图 | 目的 |
| --- | --- | --- |
| `consumable` | 实验室 + 耗材编码唯一 | 防止同一实验室编码重复 |
| `consumable` | 实验室 + 状态 + 名称 | 支持耗材列表查询 |
| `consumable_stock` | 耗材标识唯一 | 保证一种耗材一条当前库存 |
| `stock_inbound` | 入库单号唯一 | 防止业务单号重复 |

| `return_request` | 退回单号唯一 | 防止业务单号重复 |

## 15. 核心数据库不变量

1. 一种耗材只能有一条当前库存；
2. 当前库存和库存下限不能小于零；
3. 入库、领用和退回数量必须大于零；
4. 领用成功后当前库存不能小于零；
5. 累计退回数量不能超过原领用数量；
6. 退回耗材、实验室和申请人必须与原领用业务一致；
7. 一张已确认业务单只能生成一条库存流水；
8. 流水的变化前数量加变化量必须等于变化后数量；
9. 业务状态、当前库存和流水必须处于同一事务；
10. 已确认业务和库存流水不能被普通修改或删除。

## 16. Redis 在库存模块中的职责

Redis 可以用于防止按钮快速重复提交，或者降低热门耗材的请求压力，但不能代替数据库条件扣减。

原因包括：

- Redis 锁可能过期；
- 服务可能在获得锁后宕机；
- 某些内部任务可能没有经过同一把锁；
- 最终库存仍保存在 MySQL。

因此：

```text
Redis：快速拦截重复请求、减少竞争
数据库：条件扣减、事务回滚、最终库存正确性
```

## 17. 本任务暂不决定

- 数量字段的具体精度和小数位；
- 主键和业务单号生成方式；
- 最终外键和索引 DDL；
- 流水多态引用是否改为多个外键；
- 是否需要盘点和库存调整业务；
- 低库存事件的最终发布实现；
- 并发失败时是否自动重试。

盘点调整会直接影响台账可信度，第一版不以“管理员直接修改库存”的方式实现。确有需要时必须作为独立业务单据设计。
