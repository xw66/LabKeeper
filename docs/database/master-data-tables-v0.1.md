# LabKeeper 基础资料表字段候选 v0.1

> 范围：用户、权限、实验室和设备基础资料。本文不是最终表结构，也不包含建表 SQL。

## 1. 本任务解决的问题

概念模型只说明“系统中有哪些对象”。本任务进一步确定这些对象需要保存哪些信息，以及每个字段承担什么业务责任。

当前只设计以下 8 张候选表：

1. 用户 `sys_user`；
2. 角色 `sys_role`；
3. 权限 `sys_permission`；
4. 角色权限关系 `sys_role_permission`；
5. 角色授权 `sys_role_assignment`；
6. 实验室 `laboratory`；
7. 设备类型 `equipment_type`；
8. 设备 `equipment`。

预约和库存表将在后续任务中单独设计。

## 2. 通用设计约定

### 2.1 字段分类

当前用逻辑类型表达字段用途，不提前绑定具体 MySQL 类型：

| 逻辑类型 | 含义 |
| --- | --- |
| 标识 | 主键或外键引用 |
| 短文本 | 编码、名称等较短内容 |
| 长文本 | 描述、备注等内容 |
| 状态 | 数量有限且受业务规则控制的取值 |
| 时间 | 创建、更新、授权或登录时间 |

### 2.2 审计字段

需要维护的主数据原则上包含：

- `created_at`：创建时间；
- `updated_at`：最后更新时间；
- `created_by`：创建人；
- `updated_by`：最后修改人。

纯关系表可以只保留创建人和创建时间。具体是否由应用填写或数据库自动填写，后续再决定。

### 2.3 删除原则

用户、角色、实验室、设备类型和设备一旦产生业务引用，就不允许普通物理删除。第一版使用状态字段表示启用、停用或维修，避免历史预约和日志失去关联。

## 3. 用户表 `sys_user`

### 3.1 业务职责

保存能够登录系统并参与业务操作的人员账号。用户身份与角色分开保存，一个用户可以拥有多个角色。

### 3.2 字段候选

| 字段 | 逻辑类型 | 必填 | 唯一性意图 | 说明 |
| --- | --- | ---: | --- | --- |
| `id` | 标识 | 是 | 主键 | 用户内部标识，不使用用户名作为主键 |
| `username` | 短文本 | 是 | 全局唯一 | 登录名，创建后原则上不随意修改 |
| `password_hash` | 短文本 | 是 | 否 | 只保存密码哈希，不保存明文密码 |
| `display_name` | 短文本 | 是 | 否 | 页面和操作日志展示的姓名 |
| `campus_no` | 短文本 | 否 | 非空时唯一 | 学号或工号，不作为登录必需条件 |
| `email` | 短文本 | 否 | 暂定非空时唯一 | 预留通知或账号恢复能力 |
| `status` | 状态 | 是 | 否 | `ACTIVE` 或 `DISABLED` |
| `last_login_at` | 时间 | 否 | 否 | 最近一次成功登录时间 |
| `created_at` | 时间 | 是 | 否 | 创建时间 |
| `updated_at` | 时间 | 是 | 否 | 最后更新时间 |
| `created_by` | 标识 | 否 | 否 | 创建该账号的管理员 |
| `updated_by` | 标识 | 否 | 否 | 最后修改该账号的管理员 |

### 3.3 明确不保存

- 明文密码；
- JWT 或登录令牌；
- 当前角色名称字符串；
- 用逗号拼接的角色列表；
- 与项目无关的身份证号、家庭住址等敏感信息。

令牌属于登录会话数据，角色属于关系数据，都不应塞进用户表。

## 4. 角色表 `sys_role`

### 4.1 业务职责

描述一组业务职责，例如系统管理员、普通成员、实验室管理员和耗材管理员。

### 4.2 字段候选

| 字段 | 逻辑类型 | 必填 | 唯一性意图 | 说明 |
| --- | --- | ---: | --- | --- |
| `id` | 标识 | 是 | 主键 | 角色内部标识 |
| `role_code` | 短文本 | 是 | 全局唯一 | 稳定程序编码，例如 `LAB_ADMIN` |
| `role_name` | 短文本 | 是 | 暂定全局唯一 | 页面显示名称 |
| `scope_type` | 状态 | 是 | 否 | `GLOBAL` 或 `LABORATORY` |
| `description` | 长文本 | 否 | 否 | 角色职责说明 |
| `status` | 状态 | 是 | 否 | `ACTIVE` 或 `DISABLED` |
| `created_at` | 时间 | 是 | 否 | 创建时间 |
| `updated_at` | 时间 | 是 | 否 | 最后更新时间 |
| `created_by` | 标识 | 否 | 否 | 创建人 |
| `updated_by` | 标识 | 否 | 否 | 最后修改人 |

`scope_type` 用于说明授权是否必须关联实验室：

- `SYSTEM_ADMIN` 使用 `GLOBAL`；
- `MEMBER`、`LAB_ADMIN` 和 `MATERIAL_ADMIN` 使用 `LABORATORY`。

## 5. 权限表 `sys_permission`

### 5.1 业务职责

保存后端可校验的细粒度操作能力。角色是权限集合，接口不应只依赖中文角色名称判断。

### 5.2 字段候选

| 字段 | 逻辑类型 | 必填 | 唯一性意图 | 说明 |
| --- | --- | ---: | --- | --- |
| `id` | 标识 | 是 | 主键 | 权限内部标识 |
| `permission_code` | 短文本 | 是 | 全局唯一 | 例如 `reservation:approve` |
| `permission_name` | 短文本 | 是 | 否 | 页面展示名称 |
| `module` | 短文本 | 是 | 否 | 所属模块，例如预约或库存 |
| `description` | 长文本 | 否 | 否 | 权限作用说明 |
| `status` | 状态 | 是 | 否 | `ACTIVE` 或 `DISABLED` |
| `created_at` | 时间 | 是 | 否 | 创建时间 |
| `updated_at` | 时间 | 是 | 否 | 最后更新时间 |

权限通常随程序版本初始化，不允许普通用户随意创建任意权限编码。

## 6. 角色权限关系表 `sys_role_permission`

### 6.1 业务职责

建立角色与权限之间的多对多关系。

### 6.2 字段候选

| 字段 | 逻辑类型 | 必填 | 唯一性意图 | 说明 |
| --- | --- | ---: | --- | --- |
| `role_id` | 标识 | 是 | 组合唯一 | 关联角色 |
| `permission_id` | 标识 | 是 | 组合唯一 | 关联权限 |
| `created_at` | 时间 | 是 | 否 | 分配时间 |
| `created_by` | 标识 | 否 | 否 | 分配人 |

`role_id + permission_id` 不能重复。是否额外增加独立主键，留到主键设计任务决定。

## 7. 角色授权表 `sys_role_assignment`

### 7.1 业务职责

说明哪个用户在哪个数据范围内拥有什么角色。这张表同时解决多角色和实验室数据权限问题。

### 7.2 字段候选

| 字段 | 逻辑类型 | 必填 | 唯一性意图 | 说明 |
| --- | --- | ---: | --- | --- |
| `id` | 标识 | 是 | 主键 | 授权记录标识 |
| `user_id` | 标识 | 是 | 参与组合唯一 | 被授权用户 |
| `role_id` | 标识 | 是 | 参与组合唯一 | 被授予角色 |
| `laboratory_id` | 标识 | 条件必填 | 参与组合唯一 | 实验室级角色的数据范围 |
| `status` | 状态 | 是 | 否 | `ACTIVE` 或 `REVOKED` |
| `assigned_at` | 时间 | 是 | 否 | 授权时间 |
| `assigned_by` | 标识 | 否 | 否 | 执行授权的管理员 |
| `revoked_at` | 时间 | 否 | 否 | 撤销时间 |

业务约束：

- 全局角色的 `laboratory_id` 必须为空；
- 实验室级角色的 `laboratory_id` 必须有值；
- 同一用户不能重复拥有相同角色和相同数据范围；
- 撤销授权保留历史记录，不直接删除。

MySQL 唯一索引对空值的处理会影响全局角色的唯一性，具体约束方案将在索引任务中单独分析。

## 8. 实验室表 `laboratory`

### 8.1 业务职责

作为设备、耗材、预约和角色授权的数据范围边界。

### 8.2 字段候选

| `laboratory_code` | 短文本 | 是 | 全局唯一 | 稳定编码，例如 `LAB-A101` |
| `laboratory_name` | 短文本 | 是 | 暂定全局唯一 | 实验室名称 |
| `location` | 短文本 | 是 | 否 | 楼栋、房间等位置 |
| `description` | 长文本 | 否 | 否 | 使用范围或注意事项 |
| `status` | 状态 | 是 | 否 | `ACTIVE` 或 `DISABLED` |
| `created_at` | 时间 | 是 | 否 | 创建时间 |
| `updated_at` | 时间 | 是 | 否 | 最后更新时间 |
| `created_by` | 标识 | 否 | 否 | 创建人 |

| `laboratory_id` | 标识 | 是 | 参与组合唯一 | 所属实验室 |
| `type_code` | 短文本 | 是 | 实验室内唯一 | 类型稳定编码 |
| `type_name` | 短文本 | 是 | 实验室内唯一 | 类型显示名称 |

| `status` | 状态 | 是 | 否 | `ACTIVE` 或 `DISABLED` |

## 10. 设备表 `equipment`

### 10.1 业务职责

保存实际可预约设备及其当前管理状态。

### 10.2 字段候选

| 字段 | 逻辑类型 | 必填 | 唯一性意图 | 说明 |
| --- | --- | ---: | --- | --- |
| `id` | 标识 | 是 | 主键 | 设备内部标识 |
| `laboratory_id` | 标识 | 是 | 否 | 所属实验室 |
| `equipment_type_id` | 标识 | 是 | 否 | 所属设备类型 |
| `equipment_code` | 短文本 | 是 | 全局唯一 | 用于搜索、标签或二维码的稳定编码 |
| `equipment_name` | 短文本 | 是 | 否 | 设备显示名称 |
| `asset_no` | 短文本 | 否 | 非空时唯一 | 学校或工作室资产编号 |
| `model` | 短文本 | 否 | 否 | 设备型号 |
| `manufacturer` | 短文本 | 否 | 否 | 制造商 |
| `location` | 短文本 | 是 | 否 | 设备在实验室内的具体位置 |
| `status` | 状态 | 是 | 否 | `AVAILABLE`、`MAINTENANCE` 或 `DISABLED` |
| `description` | 长文本 | 否 | 否 | 使用说明或注意事项 |
| `created_at` | 时间 | 是 | 否 | 创建时间 |
| `updated_at` | 时间 | 是 | 否 | 最后更新时间 |

设备表不保存“当前是否空闲”字段。是否空闲应由设备状态、查询时间和有效预约时间片共同计算，避免缓存式字段与预约数据不一致。

## 11. 关键跨表规则

### 11.1 设备类型必须属于同一实验室

设备同时保存 `laboratory_id` 和 `equipment_type_id`，必须保证设备类型属于同一个实验室。后续需要比较：

- 仅由业务代码校验；
- 使用包含实验室标识的组合外键；
- 调整模型减少重复实验室标识。

在确定约束前不能假设普通外键会自动保证这一点。

### 11.2 角色范围必须匹配

```text
角色 scope_type = GLOBAL
    ⇒ laboratory_id 必须为空

角色 scope_type = LABORATORY
    ⇒ laboratory_id 必须有值
```

这个规则涉及两张表，普通非空约束无法单独完成，需要数据库约束与业务校验配合。

### 11.3 历史引用阻止物理删除

- 用户有预约或操作日志后不能物理删除；
- 实验室有设备或耗材后不能物理删除；
- 设备类型被设备引用后不能物理删除；
- 设备有预约后不能物理删除。

## 12. 示例授权数据

```text
用户：张老师

授权1：
角色 = LAB_ADMIN
实验室 = LAB-A101

授权2：
角色 = MATERIAL_ADMIN
实验室 = LAB-B203
```

这表示同一个人在 A101 可以审批设备预约，在 B203 可以管理耗材，但不能因此审批 B203 的设备预约。

## 13. 本任务暂不决定

- 主键使用何种 MySQL 类型；
- 文本字段的具体长度；
- 状态使用数字还是字符串保存；
- 外键级联策略；
- 唯一索引和普通索引的最终名称与顺序；
- 是否使用逻辑删除字段；
- MyBatis-Plus 自动填充的具体实现。

这些内容将在主键、字段类型和索引任务中逐步确定，不提前生成最终 SQL。
