# LabKeeper 预约表与冲突约束设计 v0.1

> 范围：预约主表、预约时间片锁表、违约记录表。本文不包含最终建表 SQL。

## 1. 本任务解决的问题

预约模块不能只保存开始时间和结束时间，还必须同时解决：

1. 保存审批、取消、签到和归还的业务状态；
2. 记录关键操作人和操作时间；
3. 在两个并发请求都通过“查询无冲突”时，由数据库保证最终只有一个成功；
4. 预约完成后保留违约历史，同时允许释放时间片占用。

本设计采用固定 30 分钟时间片，将一个预约转换为多条可建立唯一约束的占用记录。

## 2. 为什么预约主表上的普通唯一索引不够

假设为预约表建立以下唯一性意图：

```text
设备 + 开始时间 + 结束时间 唯一
```

它只能阻止两个完全相同的预约，不能阻止部分重叠：

```text
预约 A：09:00～10:00
预约 B：09:30～10:30
```

两条记录的开始时间和结束时间都不同，普通唯一索引会认为它们不重复，但业务上 09:30～10:00 已经冲突。

仅执行下面的流程同样不安全：

```text
查询是否冲突
如果不冲突，则插入预约
```

两个并发事务可能同时查询到“没有冲突”，然后都插入成功。这是典型的检查与写入之间存在竞态条件。

## 3. 预约主表 `reservation`

### 3.1 业务职责

保存预约的申请信息、时间范围、当前状态以及审批、取消、签到和归还结果。它是预约历史的长期记录，即使时间片锁释放也不能删除。

### 3.2 字段候选

| 字段 | 逻辑类型 | 必填 | 唯一性意图 | 说明 |
| --- | --- | ---: | --- | --- |
| `id` | 标识 | 是 | 主键 | 预约内部标识 |
| `reservation_no` | 短文本 | 是 | 全局唯一 | 对外展示和排查问题的业务单号 |
| `applicant_id` | 标识 | 是 | 否 | 预约申请人 |
| `laboratory_id` | 标识 | 是 | 否 | 实验室数据范围及历史快照关联 |
| `equipment_id` | 标识 | 是 | 否 | 被预约设备 |
| `start_at` | 时间 | 是 | 否 | 预约开始时间，包含在预约区间内 |
| `end_at` | 时间 | 是 | 否 | 预约结束时间，不包含在预约区间内 |
| `purpose` | 长文本 | 是 | 否 | 使用目的 |
| `status` | 状态 | 是 | 否 | 当前预约状态 |
| `reviewed_by` | 标识 | 否 | 否 | 审批通过或驳回的管理员 |
| `reviewed_at` | 时间 | 否 | 否 | 审批处理时间 |
| `review_reason` | 长文本 | 否 | 否 | 驳回原因或审批备注 |
| `cancelled_by` | 标识 | 否 | 否 | 取消操作人 |
| `cancelled_at` | 时间 | 否 | 否 | 取消时间 |
| `cancel_reason` | 长文本 | 否 | 否 | 取消原因 |
| `checked_in_by` | 标识 | 否 | 否 | 确认签到的管理员 |
| `checked_in_at` | 时间 | 否 | 否 | 实际签到时间 |
| `returned_by` | 标识 | 否 | 否 | 确认归还的管理员 |
| `returned_at` | 时间 | 否 | 否 | 实际归还时间 |
| `return_condition` | 长文本 | 否 | 否 | 设备归还状况 |
| `version` | 版本 | 是 | 否 | 候选并发控制字段 |
| `created_at` | 时间 | 是 | 否 | 创建时间 |
| `updated_at` | 时间 | 是 | 否 | 最后更新时间 |

`laboratory_id` 必须与设备所属实验室一致。它保留在预约表中，便于数据权限查询和历史统计，但不能只依靠前端传值，后端必须从设备信息校验。

### 3.3 状态候选

| 状态 | 含义 | 是否持有时间片锁 |
| --- | --- | ---: |
| `PENDING` | 待审批 | 是 |
| `APPROVED` | 已通过，待签到 | 是 |
| `REJECTED` | 已驳回 | 否 |
| `CANCELLED` | 已取消 | 否 |
| `CHECKED_IN` | 使用中 | 是 |
| `OVERDUE` | 已逾期未归还 | 是 |
| `COMPLETED` | 已归还完成 | 否 |
| `NO_SHOW` | 未签到违约 | 否 |

时间片锁表示当前业务占用，不承担历史审计职责。开始时间、结束时间和状态历史事实由预约主表、违约记录及操作日志保存。

## 4. 预约时间片锁表 `reservation_slot`

### 4.1 业务职责

将连续预约区间拆成固定 30 分钟的占用单元，使数据库能够使用普通唯一约束阻止重叠。

预约区间统一采用左闭右开语义：

```text
[start_at, end_at)
```

因此 09:00～10:00 和 10:00～11:00 不冲突。

### 4.2 字段候选

| 字段 | 逻辑类型 | 必填 | 唯一性意图 | 说明 |
| --- | --- | ---: | --- | --- |
| `id` | 标识 | 待定 | 主键候选 | 是否需要独立主键后续决定 |
| `reservation_id` | 标识 | 是 | 否 | 所属预约 |
| `equipment_id` | 标识 | 是 | 参与组合唯一 | 被占用设备 |
| `slot_start` | 时间 | 是 | 参与组合唯一 | 30 分钟时间片起点 |
| `created_at` | 时间 | 是 | 否 | 占用创建时间 |

最重要的唯一性意图是：

```text
equipment_id + slot_start 唯一
```

同一设备同一时间片只能存在一条占用记录。

### 4.3 拆分示例

预约 09:00～10:30 时，按时间升序生成：

```text
设备A + 09:00
设备A + 09:30
设备A + 10:00
```

另一条 09:30～11:00 的预约需要插入：

```text
设备A + 09:30  ← 与已有唯一键冲突
设备A + 10:00  ← 与已有唯一键冲突
设备A + 10:30
```

只要任意时间片冲突，整条新预约都必须失败。

## 5. 创建预约的事务流程

创建预约必须在一个数据库事务中执行：

```text
1. 校验用户权限、设备状态和时间规则
2. 插入 PENDING 预约主记录
3. 按升序生成所有 30 分钟时间片
4. 批量插入 reservation_slot
5. 全部成功后提交事务
```

失败规则：

```text
如果任一时间片触发唯一约束冲突：
    回滚预约主记录
    回滚已经插入的其他时间片
    返回“该设备时间段已被占用”
```

预约主记录不会在冲突后孤立保留。数据库异常需要由全局异常处理转换成稳定的业务错误，不能把底层索引名称直接返回给前端。

### 5.1 并发时会发生什么

假设请求 A 和请求 B 同时预约相同时间：

```text
A 查询无冲突
B 查询无冲突
A 尝试插入时间片
B 尝试插入相同时间片
```

最终数据库唯一约束只允许一个事务获得该时间片。另一个事务会等待后失败，或直接得到重复键错误，并整体回滚。

这意味着“提前查询”只用于给用户更友好的提示，数据库唯一约束才是最终正确性保障。

### 5.2 时间片插入顺序

同一预约的时间片必须按 `slot_start` 升序插入。不同事务采用一致顺序可以降低相互交叉等待和死锁概率，但不能保证绝对没有死锁；后续仍需把死锁作为可识别的数据库并发错误处理。

## 6. 时间片锁释放规则

以下转换需要在同一事务中更新预约状态并删除该预约的时间片锁：

```text
PENDING  → REJECTED
PENDING  → CANCELLED
APPROVED → CANCELLED
APPROVED → NO_SHOW
CHECKED_IN / OVERDUE → COMPLETED
```

事务伪代码：

```text
按“预约ID + 预期当前状态”更新预约
如果影响行数不是1：
    拒绝非法或重复操作

删除该预约对应的全部时间片锁
提交事务
```

删除时间片锁不等于删除预约历史。预约的开始、结束时间和最终状态仍永久保存在预约主表中。

## 7. 违约记录表 `violation_record`

### 7.1 业务职责

保存未签到和逾期的历史事实。逾期预约最终归还后可以变成 `COMPLETED`，但违约记录仍然保留。

### 7.2 字段候选

| 字段 | 逻辑类型 | 必填 | 唯一性意图 | 说明 |
| --- | --- | ---: | --- | --- |
| `id` | 标识 | 是 | 主键 | 违约记录内部标识 |
| `violation_no` | 短文本 | 是 | 全局唯一 | 违约业务编号 |
| `reservation_id` | 标识 | 是 | 参与组合唯一 | 关联预约 |
| `user_id` | 标识 | 是 | 否 | 违约用户，便于查询和统计 |
| `violation_type` | 状态 | 是 | 参与组合唯一 | `NO_SHOW` 或 `OVERDUE` |
| `occurred_at` | 时间 | 是 | 否 | 违约发生时间 |
| `handling_status` | 状态 | 是 | 否 | `PENDING` 或 `HANDLED` |
| `handled_by` | 标识 | 否 | 否 | 处理管理员 |
| `handled_at` | 时间 | 否 | 否 | 处理时间 |
| `handling_note` | 长文本 | 否 | 否 | 处理说明 |
| `created_at` | 时间 | 是 | 否 | 创建时间 |

`reservation_id + violation_type` 应保持唯一，避免定时任务重复扫描时为同一预约生成多条相同违约。

处理违约表示管理员已经跟进，不代表删除或撤销违约事实。

## 8. 状态更新的并发控制

前端传入目标状态后直接覆盖数据库是禁止的。每个操作必须明确预期当前状态，例如：

```text
审批通过：只有 PENDING 可以变成 APPROVED
签到：只有 APPROVED 可以变成 CHECKED_IN
归还：只有 CHECKED_IN 或 OVERDUE 可以变成 COMPLETED
```

更新时需要同时检查预约标识和当前状态。影响行数为零通常表示：

- 预约不存在；
- 已被另一个请求处理；
- 当前状态不允许执行该操作。

候选 `version` 字段可用于普通编辑的乐观锁，但预约状态机仍应保留“预期当前状态”条件，因为它表达的是业务合法性，而不只是数据版本。

## 9. Redis 在预约冲突中的职责

Redis 可以承担：

- 防止用户快速重复点击；
- 减少热门设备的大量请求同时进入数据库；
- 在高并发下提供短时间的设备级互斥。

Redis 不能代替数据库时间片唯一约束，因为：

- 锁可能过期；
- 服务可能在获得锁后宕机；
- Redis 可能不可用或发生主从切换；
- 程序错误可能绕过加锁代码。

因此正确性边界是：

```text
Redis：减少重复和竞争，改善性能
数据库唯一约束：保证最终不能出现重叠预约
```

## 10. 索引意图

当前只记录查询目标，不确定最终索引名称和字段顺序：

| 表 | 索引意图 | 服务的查询 |
| --- | --- | --- |
| `reservation` | `reservation_no` 唯一 | 按业务单号查询 |
| `reservation` | 申请人 + 创建时间 | 查询我的预约 |
| `reservation` | 实验室 + 状态 + 开始时间 | 管理员审批和日程列表 |
| `reservation` | 设备 + 开始时间 | 查看设备预约历史 |
| `reservation_slot` | 设备 + 时间片起点唯一 | 阻止重叠并查询占用 |
| `reservation_slot` | 预约标识 | 状态结束时批量释放锁 |
| `violation_record` | 预约 + 违约类型唯一 | 防止重复生成违约 |
| `violation_record` | 用户 + 处理状态 + 发生时间 | 查询用户违约和待处理记录 |

索引不是越多越好。每个额外索引都会增加插入时间片和更新预约的成本，最终需要结合真实查询与执行计划验证。

## 11. 核心数据库不变量

1. `start_at` 必须早于 `end_at`；
2. 开始和结束时间必须对齐到 30 分钟边界；
3. 预约时长必须为 30 分钟至 4 小时；
4. 预约设备必须属于预约实验室；
5. 同一设备同一时间片只能有一条锁记录；
6. 处于占用状态的预约必须拥有完整时间片锁；
7. 释放状态的预约不能继续持有时间片锁；
8. 预约状态只能按状态机转换；
9. 同一预约同一违约类型只能记录一次；
10. 实验室管理员不能审批自己的预约。

其中部分规则可由单表约束完成，部分必须由事务、外键、唯一索引和业务校验共同完成。后续不能声称“所有业务规则都只靠数据库约束”。

## 12. 方案代价

时间片方案会增加记录数量：一次最长 4 小时的预约会产生最多 8 条时间片记录。

对于学校实验室或小型工作室，这个数量可控，换来的好处是：

- 冲突规则直观；
- 可以使用普通唯一索引提供最终保障；
- 并发测试结果容易解释；
- 不依赖复杂的区间锁实现。

如果未来允许任意分钟或跨天预约，需要重新评估时间片粒度和数据量，不能直接沿用当前结论。

## 13. 本任务暂不决定

- 字段的具体 MySQL 类型和长度；
- 主键和业务单号的生成策略；
- 唯一索引及普通索引的最终 DDL；
- 时间字段使用何种 Java 和 MySQL 类型；
- Redis 锁键、超时时间和续期策略；
- 违约是否自动限制后续预约；
- 最终异常码和前端提示文案。

这些问题将在后续字段类型、索引和业务实现任务中逐项确认。
